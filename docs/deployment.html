نشر GO COURSE

الخادم: Render · الواجهة: Vercel · البيانات والملفات الجديدة: Neon

تم تجهيز الكود والملفات؛ لم يُنشَر المشروع على حساباتك ولم يُختبر اتصال Neon الحقيقي بعد. لا تضع رابط قاعدة البيانات أو المفتاح السري للمصادقة في الواجهة أو Git. استعمل قاعدة Neon فارغة لأول تشغيل.

1. المتطلبات

  1. ارفع المستودع إلى GitHub لربطه بالاستضافتين. يجب تضمين pnpm-lock.yaml وlib/db/migrations وapi والملفين render.yaml وvercel.json.
  2. Runtime: Node.js 22، ومدير الحزم pnpm 10.26.1 مثبت في packageManager.
  3. من Neon انسخ رابط PostgreSQL المباشر Direct مع TLS: ?sslmode=require. يمكن استخدامه في التشغيل والترحيلات معًا.
  4. إذا استعملت رابط Neon من نوع Pooled في DATABASE_URL، تختار التهيئة تلقائيًا نظيره المباشر بحذف -pooler من اسم المضيف فقط؛ لا تتغير بيانات الدخول أو إعدادات TLS. يمكن تحديد اتصال بديل عبر DATABASE_MIGRATION_URL. الترحيلات تحتاج اتصالًا ثابتًا لقفلها ومنع تشغيلها المتزامن، بينما يستمر التشغيل العادي بالرابط الأصلي.
  5. للنشر الخارجي، استخدم تطبيق Clerk مستقل بمفاتيح مطابقة للواجهة والخادم، واضبط دومين Vercel في إعداداته. لا تُحذف إعدادات Clerk الحالية في Replit؛ تبقى للمعاينة. الحسابات وكلمات المرور القديمة لا تنتقل تلقائيًا بين تطبيقي المصادقة.

2. Backend على Render

أنشئ Web Service من المستودع أو Blueprint باستخدام render.yaml. اختر Node، واترك Root Directory فارغًا: العمل من جذر المستودع وليس مجلد api-server.

Build Command

pnpm install --frozen-lockfile && pnpm run build:render

Start Command

pnpm run start:render

هذا الأمر يشغّل ترحيلات الجداول وتهيئة اللغات والمستويات مرة واحدة بصورة آمنة قابلة للإعادة، ثم يشغّل الخادم. إذا فشلت تهيئة القاعدة لا يبدأ الخادم بنجاح زائف. لا يستعمل push-force ولا يمسح السجلات.

Health Check Path: /api/readyz؛ يفحص إمكانية قراءة الجداول من القاعدة. Render يوفّر PORT تلقائيًا.

متغير Renderالقيمة أو المعنى
DATABASE_URLرابط Neon السري مع TLS، وهو رابط التشغيل الأساسي. لا تضفه إلى Vercel.
DATABASE_MIGRATION_URLاختياري لتجاوز اتصال الترحيلات. رابط Neon المجمّع يُحوّل تلقائيًا إلى نظيره المباشر للتهيئة فقط. إذا غاب DATABASE_URL، يُستخدم هذا الرابط للتشغيل مؤقتًا.
CLERK_SECRET_KEYالمفتاح السري لتطبيق Clerk الخارجي؛ يبقى على الخادم.
CLERK_PUBLISHABLE_KEYالمفتاح العام لنفس تطبيق Clerk.
OWNER_EMAILبريد المالك المؤكد الذي يحصل على صلاحيات المدير عند الدخول.
FRONTEND_URLرابط Vercel الكامل مثل https://your-app.vercel.app دون / أخيرة. إن أضفت دومينًا مخصصًا فاستخدم قائمة أصول محددة مفصولة بفواصل، لا wildcard.
PUBLIC_API_URLرابط Render الكامل مثل https://your-api.onrender.com دون /api ودون / أخيرة.
AUTH_MODEexternal
FILE_STORAGE_PROVIDERdatabase
NODE_ENVproduction
NODE_VERSION22
DB_POOL_MAX5؛ اجمع عدد الاتصالات عند زيادة عدد الخوادم.

يمكن تجهيز الخدمتين أولًا للحصول على الرابطين، ثم تحديث FRONTEND_URL وPUBLIC_API_URL وإعادة نشر Render. فشل فحص الجاهزية قبل إكمال المتغيرات مقصود، وليس نجاحًا وهميًا.

3. Frontend على Vercel

استورد المستودع نفسه. Root Directory هو جذر المستودع ./ وFramework Preset هو Other. تُقرأ الإعدادات من vercel.json، بما فيها مسارات SPA حتى يعمل تحديث صفحة داخلية مباشرة.

Install Command

pnpm install --frozen-lockfile

Build Command

pnpm run build:vercel

Output Directory

artifacts/go-course/dist/public

لا يوجد Start Command على Vercel: الواجهة ملفات ثابتة، ومسارات API تستخدم جسر Edge إلى Render. لا تستعمل vite preview كخادم إنتاج.

متغير Vercelالقيمة
BACKEND_URLرابط Render نفسه المستخدم في PUBLIC_API_URL، دون /api. العنوان الافتراضي للمشروع هو https://go-course-ze56.onrender.com؛ يمكن تغييره بهذا المتغير. هذا عنوان خادمي عام وليس سر قاعدة بيانات.
VITE_AUTH_MODEexternal
VITE_CLERK_PUBLISHABLE_KEYنفس المفتاح العام الموجود في Render.

لا تضف DATABASE_URL أو CLERK_SECRET_KEY إلى Vercel، ولا تسبق الأسرار بـ VITE_. لا تضبط VITE_CLERK_PROXY_URL في النشر الخارجي. بعد تعديل متغير VITE_ أعد بناء الواجهة لأن قيمته تُضمّن أثناء البناء.

4. ربط البيانات والملفات

  • كل بيانات الأعمال تُقرأ وتُكتب بواسطة Render في PostgreSQL المشار إليه بـ DATABASE_URL؛ لا اتصال مباشر بين متصفح الطالب وNeon.
  • البيانات التعليمية والمالية والأدوار والروابط والتخصصات والملفات محفوظة في ستة جداول، تشمل جدولًا خاصًا ببايتات الملفات داخل Neon.
  • الصور والمرفقات الجديدة حتى 50MB تذهب مباشرة إلى Render برابط موقّع لمدة عشر دقائق؛ لا تُحفظ على قرص Render المؤقت، ولا تمر بايتاتها عبر حدود طلبات Vercel.
  • قراءة ملف خاص تبدأ بفحص صلاحيات الحساب والاشتراك، ثم التحويل إلى رابط تحميل مؤقت. الرفع لمرة واحدة مع تحقق من الحجم ونوع الصورة/PDF؛ الصوت والفيديو يدعمان طلبات Range.
  • تخزين الفيديوهات في قاعدة البيانات يستهلك مساحة وذاكرة ونقلًا أكثر. راقب حدود Neon؛ ينصح لاحقًا بمخزن ملفات متخصص إذا أصبح حجم الوسائط كبيرًا.
  • كلمات المرور والجلسات تديرها Clerk ولا تُخزّن كنص داخل Neon.
  • توصيل قاعدة جديدة لا ينقل بيانات قاعدة Replit القديمة أو الملفات القديمة تلقائيًا. إن كانت لديك بيانات فعلية، انسخها احتياطيًا وخطّط لترحيل منفصل قبل تبديلها؛ لا تشغّل الترحيل الابتدائي فوق مخطط موجود دون مراجعته.

5. التحقق بعد النشر

curl https://YOUR-API.onrender.com/api/readyz
curl https://YOUR-FRONTEND.vercel.app/api/readyz

يُفترض أن يعيدا {"status":"ok","database":"connected"}. ثم افتح كتالوج اللغات، ادخل ببريد المالك وأكّد البريد، أنشئ أستاذًا ودورة وطالبًا، ارفع صورة، واختبر استمرار البيانات بعد إعادة تشغيل Render.

اختبر الدعوات واستعادة كلمة المرور والروابط من دومين الإنتاج الحقيقي. لا يكفي نجاح البناء لإثبات نجاح المصادقة.

6. أوامر إضافية

# من جذر المستودع، بعد ضبط المتغيرات في بيئة آمنة
pnpm run typecheck
pnpm --filter @workspace/api-server test

# بناء الخادم ثم تهيئة قاعدة جديدة دون تشغيل الخادم
pnpm run build:render
pnpm run db:setup

# توليد ترحيل جديد عند تغيير المخطط، ومراجعة SQL قبل نشره
pnpm --filter @workspace/db run generate

لا تُشغّل db:setup فوق قاعدة التطوير الحالية التي أُنشئت سابقًا بـ db push؛ خط الترحيل الأول موجّه لقاعدة جديدة. لا تستعمل push-force مع بيانات فعلية.

خطط للنسخ الاحتياطي واختبار الاستعادة. التذكيرات تعمل أثناء بقاء خدمة Render مشغّلة؛ الخدمة التي تتوقف عند الخمول تؤخر إرسالها حتى التشغيل التالي.
